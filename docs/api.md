# API

JSON over HTTPS. A request is made by a user (`sid` cookie or `Authorization: Bearer`), a guest (`gid` cookie, or IP in IP mode), or anonymously; see [auth.md](auth.md).

- Errors: `{ "error": { "code": "snake_case", "message": "…" } }`, with the appropriate HTTP status. A few errors carry more fields in the same object (`409 needs_classification`, below).
- `409 needs_classification` ("Choose what kind of video this is before adding it to a library"; [media-types.md](media-types.md#media-types)): an add to a library of an `uncategorized` video without `mediaType`. The error has `itemId` and, when something is known, `suggested: {mediaType, show?: {name?, season?, episode?}}` (yt-dlp's `series`/`season_number`/`episode_number` → `show`, its `track`/`artist` → `music_video`, an upload's file name with `SxxEyy` → `show`). Every add to a library takes `mediaType` (`audio`, `music_video`, `movie` or `show`; not `uncategorized`: `400 invalid_media_type`) and `show {name, season?, episode}` (for and only for `show`: `400 show_required` / `not_a_show` / `invalid_show`); they are applied only when the item needs them (an item already classified, or already in that library, never asks, and a type sent along is ignored). For `PUT /api/library/{itemId}` nothing has happened: send it again with the type. For a YouTube import and an upload (`complete`, or the pre-check of `POST /api/uploads`, whose error also has `uploadId`) the import or upload went through as with `addToLibrary: false`; finish with `PUT /api/library/{itemId} {mediaType, show?}`. Requests from a pasted link in a room (no library) never ask. The classification is audited as `item.updated` (`classifiedOnLibraryAdd: true`).
- `507 insufficient_storage` ("The server is low on disk space; adding media is paused."): starting an upload, an upload chunk or a new YouTube fetch while the data volume is below `storage.minFreeBytes` ([library-and-ingest.md](library-and-ingest.md#free-disk-space)). The same code comes back as a WebSocket `error` for a room's `queue.add` with a `youtubeUrl` (or a purged YouTube item).
- List endpoints use cursor pagination: `?cursor=…&limit=…` → `{ items, nextCursor }`.
- **No response contains an IP address**, except the endpoints marked *ip.view*.

Actors are serialised as `{ "kind": "user"|"guest", "id", "name", "isGuest" }` (`name`: a user's display name or a guest's name; `isGuest` drives the guest badge). Nothing else about an actor (no IP, no guest mode or ban flag) is in this form.

## Live (no session; slug or token in path)

`GET/HEAD /live/{key}.ts` · `GET /live/{key}/index.m3u8` · `GET /live/{key}/seg/{seq}.ts` · `GET/HEAD /live/{key}.mp3`

`{key}` is the room's slug (public and unlisted rooms) or the output's token (private rooms) ([stream URLs](program-output.md#stream-urls)). Every request counts against a per-IP rate limit (burst 60, then 10/s; IPv6 by /64) before the key is looked up: `429 rate_limited` with `Retry-After`. A URL has at most 64 concurrent connections (`.ts` and MP3 streams for their whole life, HLS requests while served): `429 too_many_connections`, `Retry-After: 10`. Unknown keys, a token of a public/unlisted room or the slug of a private one, disabled outputs, rotated tokens, old slugs and kinds the server switched off: `404`.

`.mp3` ([program-output.md](program-output.md#mp3-internet-radio-players)): `200`, `Content-Type: audio/mpeg`, close-delimited (no `Content-Length`, no `Transfer-Encoding`), `icy-name` (room name, ASCII), `icy-br`, `icy-sr`, `icy-pub: 0`; whole MP3 frames from the first byte. With the request header `Icy-MetaData: 1`: `icy-metaint: 16000` and ICY metadata blocks (`StreamTitle='Artist - Title';`) every 16000 audio bytes. `HEAD`: the headers only, starts nothing. Without ffmpeg: `503 output_unavailable`.

## WebSocket

`GET /ws` (upgrade; `sid` or `gid` cookie, or anonymous). One room per socket. Requests carry `"rid"`, and are answered with `ack` or `error`.

Actions that need an identity (votes, requests, suggestions, vote-skip) are refused from an anonymous socket with error code `identity_required`. The client then calls `POST /api/me/guest`. That sets the `gid` cookie in cookie mode, and returns a single-use `identityTicket` valid for 60 s. The client sends `{type:"identity", ticket}` on the open socket and retries the action. The ticket is needed because a socket that's already open can't see a cookie set after its upgrade.

### As implemented (M3, `rooms/RoomSocket`, `RoomBroadcaster`)

- **On connect** the server sends `{type:"identity", actor?}` (no `actor` for an anonymous socket). `auth` (bearer token) is only accepted before `join` (`409 already_joined`); a bad token is `401 invalid_token`. An invalid `Authorization: Bearer` header on the upgrade is a plain HTTP `401`, never a socket.
- **`identity`**: `400 invalid_ticket` (unknown, used, expired), `409 already_identified` (a user socket, or another guest), `403 guests_disabled`. A socket in a room is then counted as the guest and gets a fresh full `state`; a guest banned from the room gets `kicked` instead.
- **Identity re-check**: before every room action the socket's session or guest is resolved again. A revoked/expired session, disabled user or deleted guest gets `kicked` `session_ended`, an `error` `session_ended`, and the socket closes (1000).
- **Replies**: `{type:"ack", rid, ...result}` / `{type:"error", rid?, status, code, message}`; `rid` may be a number or a string. Without a `rid` only errors are sent. Results: `join` → `roomId, slug, mode`; `queue.add` → `entryId, itemId, state` (`queued`/`suggested`); `queue.addPlaylist` → `entryIds, state, skipped, recentlyPlayed, overLimit` ("Add All" of one of the caller's own playlists, by the request rules: [rooms.md](rooms.md#queue-editing); `state` = `queued`/`suggested`; left out: `skipped` not playable, `recentlyPlayed` within `noRepeatWindow`, `overLimit` beyond `requestsPerActor`; guests and anonymous visitors `403 forbidden`, plus `queue.add`'s request errors); `queue.move` → `moved` (several entries in the given order before `beforeEntryId`, or to the end of `section` (default: the first entry's section); the target section is `beforeEntryId`'s, so entries move between the sections; `400 invalid_entry_ids` (none, more than 500, or one twice), `404 entry_not_found`, `409 before_entry_not_found` (not a queued entry, or not in the `section` given), `409 wrong_control_mode` in `vote` mode: [rooms.md](rooms.md#queue-editing)); `queue.request` → `state` (`queued`/`suggested`); `queue.pin` → `changed` (optional `pinned`, default `true`; `false` unpins); `vote` → `votes` (the new total); `voteSkip` → `votes, needed, skipped`; `play`/`pause`/`previous` → `changed`. Other codes: `400 invalid_message` (not a JSON object, missing/mistyped field), `409 not_joined`, `400 invalid_mode`, `400 invalid_position`, `400 invalid_vote`, `503 room_closed` (join again), `429 too_many_requests` (more than 4 `queue.add`/`queue.addPlaylist` running per socket; those two run off the socket's thread so `time` is answered meanwhile). `time` needs a numeric `t0`; it is answered at any time, also before `join`.
- **`join`**: `room` is the id or slug, `mode` defaults to `listen`. Joining another room leaves the first. Access is `GET /api/rooms/{room}`'s (`404 room_not_found` for private rooms, a banned or timed-out person joins read-only).
- **Messages per change**: every committed change sends each socket in the room exactly one message with the new `version` (consecutive): `presence` (`{presence}`) when only the counts changed; `timeline` (`{timeline, current?, skipVotes?}`) when only the timeline was re-anchored on the same entry; otherwise the full `state` while the room has at most 200 waiting entries (queue + suggestions), and above that a `queue` delta: `{upsert: [entries new or changed], removed: [entryIds], order: [queue entryIds in play order], suggestionOrder: [...], timeline, current?, history, skipVotes?, presence}` (instead of the per-op `add|remove|move|votes|status` sketch above). Room, settings and member-role changes always send the full `state`. The `state` sent on `join` carries the version before the join, the join's own presence change follows as `presence`. `sync` re-sends the full `state` (same version).
- **`state` shape**: `room: {id, slug, name, visibility, controlMode, ownerId, settings, alone?, awayInRoomId?, you: {role?, identified, canVote, canRequest, canRequestLibrary, canUpload, canYoutube, canSkip, canModerate, restriction?: {kind: "ban"|"timeout", until?}}}`, `timeline: {state, entryId?, anchorServerMs, anchorPositionMs}` (`alone: true` for the user's alone room, [rooms.md](rooms.md#alone), with `awayInRoomId` = the room the user is in while the alone state is saved; a full `state` follows every join or leave, so every device hears about it and reads `GET /api/me/play-session`), `current?: {entryId, status, item, addedBy?, addedAt, section, audioOnly?}` (absent when idle; `audioOnly: true` when the entry plays audio-only, [rooms.md](rooms.md#audio-only-rooms): its `item` then has no `videoUrl`, and a video with an audio trim has `audioUrl` = its `audio-only.m4a` and `durationMs` = that file's length; queued and suggested entries likewise), `queue`/`suggestions: [{entryId, status: ready|processing|failed|purged, item, addedBy?, addedAt, votes, pinned, section, yourVote}]` (queue in play order, suggestions oldest first; `section`: `manual` or `autoplay` ("From Playlist", [rooms.md](rooms.md#autoplay); `addedBy` is then the person whose playlist it came from), and the play order follows `autoplay.requestsFirst`), `history: [{entryId, state: played|skipped, item, addedBy?, via?, playedAt}]` (last 20, latest first; `addedBy` with the name it had then; the full history is `GET /api/rooms/{id}/history`), `skipVotes?: {entryId, votes, needed}` (vote mode with vote-skip on), `presence`, `outputs: []` (filled in M4; no `overlay` object: the management view reads it from `server-switches`, [overlay.md](overlay.md#room-ui)). `item`: `{id, kind, presentAsAudio, title, artist?, durationMs?, status, source}` plus, once `ready`, `coverUrl` (only when that version has a `cover.jpg`: not every item has one), `audioUrl`, `videoUrl` (video items; all three are the current media version's URLs, `/media/{id}/v/{N}/…`, so a play that started on them keeps its bytes after a re-encode) and, for audio uploads with a web-playable original, `originalUrl` + `originalGainDb` + `originalType` (the MIME type for `canPlayType`, by the kept file's extension, e.g. `audio/flac`, `audio/mp4; codecs="mp4a.40.2"`, `audio/ogg; codecs="opus"`; absent for an unlisted extension, the client then trusts the server).
- **`outputs` and `output.status`** (M4, `rooms/RoomOutputs`, `output/OutputStatusFeed`): `state.outputs` lists the room's **active** outputs (row enabled AND server switch), in the order rtmp, ts, hls, mp3: `{kind, status, estimatedDelayMs, detail?}`. `status`: RTMP `connecting` (also before the push has started) | `connected` | `retrying` | `error` (also when the server has no ffmpeg); `.ts`/HLS `ready`; MP3 `ready`, or `error` without ffmpeg. `estimatedDelayMs` is the room setting `estimatedDelayMs.<kind>` (defaults 5000 / 2000 / 8000 / 3000). `detail` (RTMP: the push's last ffmpeg line, key masked, or why it can't run) goes to the owner and moderators only; moderators get it with every URL replaced by `(ingest URL)` and no key hint (`RoomOutputs.moderatorDetail`), since the ingest URL and key are the owner's. A change sends `{type:"output.status", kind, status, estimatedDelayMs?, detail?}` to every socket in the room, **without a `version`** (not a room change; the client applies it to its state as is); an output that stops being active is sent once as `status: "off"` (no delay). Changes are found by comparing each room's outputs with what was last sent, after every push status change and after every outputs reconcile (API changes, admin settings saves, every 10 s). A delay setting change comes with the room's full `state`.
- **`queue.retry`** (added 2026-11-10): `{entryId}` of a queued entry or suggestion whose YouTube item failed → `ack {itemId, status: "pending"}`; the item gets a new download job, the entry keeps its place and shows "Waiting to download…" again (with the next `state`/`ingest`), and plays once ready like any entry that isn't ready. Allowed for the owner and moderators, and for whoever requested the entry while they may still add YouTube links in the room (`you.canYoutube`: a user with `library.youtube`, a guest while the server's and the room's `guests.canYoutube` allow it); others `403 forbidden`, anonymous `401 identity_required`. Errors as `POST /api/items/{id}/retry` (`404 entry_not_found` for an unknown entry). Runs off the socket's thread like `queue.add` (it can wait for an import of the same video) and counts toward the same limit of 4. Audited (`item.ingest_retried`, details with `roomId`). `item` in the room state now also carries `source` (`upload`|`youtube`), so the client knows which failed entries have a Retry button.
- **`queue.nextEpisode`** (M8, [media-types.md](media-types.md#next-episode)): owner and moderators (`403 forbidden` otherwise). The basis is the current entry's item, or with nothing current the item of the entry that started playing most recently (`409 nothing_playing` if none; `409 not_a_show` if it isn't a `show` item). The next episode is looked up in the **room owner's** library (same show name, case-insensitive; by season, then episode) and added like `queue.add` by `itemId` (`via: "library"`; a purged or failed YouTube episode is fetched again, purged or failed uploads are passed over) → `ack {entryId, itemId, state}`; `404 no_next_episode` when there is none.
- **`queue.request`** (M9, [rooms.md](rooms.md#autoplay)): ↑ on an autoplay entry turns it into the caller's request, checked like `queue.add` by `itemId` (`401 identity_required`, `403 cannot_request` / library request right, `409 request_limit`, `403 library_requests_off`; not `noRepeatWindow`): it moves to the end of the manual section (a suggestion in `owner` mode for others than the owner and moderators), `addedBy` the caller, in `vote` mode with the caller's vote; a request raises `request.new` with `via: "autoplay"`. `404 entry_not_found` (not a waiting entry), `409 not_autoplay` (a request or suggestion already). `vote` and `queue.pin` on an autoplay entry: `409 autoplay_entry`.
- **`request.new`**: `{request: {entryId, item, by?, via}}` (`via`: `library`, `upload`, `youtube`, `history`, `playlist` (one per entry of an "Add All") or `autoplay`) to sockets of the owner and moderators (no `version`; it accompanies the change's own message). The request id is gone with the request history (2026-11-10).
- **`queue.add` by `itemId`: any item on the server** (2026-11-10): no request scope (`requestScope` and `403 not_in_request_scope` are gone); unknown `404 item_not_found`, failed upload `409 item_failed`, purged upload `409 media_expired`, a purged or failed YouTube item is fetched again. With the room setting `libraryRequests` off, `403 library_requests_off` for everyone but the owner and moderators (also for `historyEntryId`); `youtubeUrl` is unaffected; `uploadId` needs the room setting `uploadRequests` (only on while `libraryRequests` is): off → `403 upload_requests_off` for everyone but the owner and moderators ([rooms.md](rooms.md#uploads-need-library-requests)). `you.canRequestLibrary` in the room state is false then (owner and moderators excepted), so the page hides the search and the history's Add to Queue.
- **`queue.add` from the history** (2026-11-10): `{historyEntryId}` instead of `itemId`/`uploadId`/`youtubeUrl` adds that entry's item again ([rooms.md](rooms.md#history)): an entry of this room that has started playing, else `404 history_entry_not_found`. Checked like a library request (guests need `guests.canRequestLibrary`, `requestsPerActor`, `noRepeatWindow`, owner mode → suggestion, `libraryRequests`); a purged YouTube item is fetched again, a purged upload is `409 media_expired`. The entry records `via: "history"`.
- **`request.progress`** (added 2026-11-10): while a `queue.add` with a `youtubeUrl` runs the `yt-dlp -J` lookup of a new video, `{type:"request.progress", rid, stage, text}` for each lookup stage, in order and each at most once, **to the requesting socket only** and before the request's `ack`/`error`; nothing without a `rid`, and nothing when there is no lookup (a known item answers at once). `stage`/`text`: `contacting` "Contacting YouTube…", `page` "Reading the video page…", `details` "Getting the video details…", `formats` "Checking formats…" ([rooms.md](rooms.md#adding-a-youtube-link)). The spec's sketch named the field `id`; it is `rid`, like `ack`.
- **`ingest`** (added 2026-11-10, `RoomBroadcaster`, `ingest/IngestProgress`): what the ingest of the room's entries whose item isn't ready (current, queued and suggested; `processing` or `failed`, not `purged`) is doing, `{type:"ingest", items: {<itemId>: {state: queued|running|failed, kind?, position?, step?, progress?, error?}}}`, to every socket in the room, **without a `version`** (not a room change). `queued`: `position` is the 1-based place in the whole ingest queue (the jobs page's); `running`: `step` `download`|`encode`|`finish` with that step's own `progress` (0..1, whole percent) once the job has named one; `failed`: `error`, the item's error cut to its first line and 120 characters. An item with no job yet is absent (it reads as waiting). Looked up at most once a second per room and only while such an entry exists; sent only when it changed, right after the full `state` to a socket that joins or `sync`s, and once more with `items: {}` when no entry waits any more. No logs, nothing about other people, no IPs. The web client shows it on the entry's badge ("Waiting to download (3rd in line)", "Downloading 45 %", "Encoding 30 %", "Finishing…", "Failed: …"; `web/src/jobtext.ts` `ingestText`, also used by the Library and item pages).
- **`kicked`** (`{reason}`) takes the socket out of the room; the socket stays open. Reasons: `room_not_found` (e.g. the room went private), `room_deleted`, `room_closed` (the room's executor stopped; join again), `session_ended` (then closed). Role changes (`PUT`/`DELETE …/members/{userId}`) now go through the room executor as a `MemberChanged` event, so they bump the room `version`. Bans and timeouts don't kick (M9): every socket in the room gets a fresh `state` with its `you.restriction`, and room actions answer `403 banned_from_room` / `403 timed_out` ([rooms.md](rooms.md#bans-and-timeouts)).
- **Slow sockets**: each socket has a bounded outbox (1024 messages); one that overflows is closed with 1008.
