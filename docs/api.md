# API

JSON over HTTPS. A request is made by a user (`sid` cookie or `Authorization: Bearer`), a guest (`gid` cookie, or IP in IP mode), or anonymously; see [auth.md](auth.md).

- Errors: `{ "error": { "code": "snake_case", "message": "…" } }`, with the appropriate HTTP status.
- `507 insufficient_storage` ("The server is low on disk space; adding media is paused."): starting an upload, an upload chunk or a new YouTube fetch while the data volume is below `storage.minFreeBytes` ([library-and-ingest.md](library-and-ingest.md#free-disk-space)). The same code comes back as a WebSocket `error` for a room's `queue.add` with a `youtubeUrl` (or a purged YouTube item).
- List endpoints use cursor pagination: `?cursor=…&limit=…` → `{ items, nextCursor }`.
- **No response contains an IP address**, except the endpoints marked *ip.view*.

Actors are serialised as `{ "kind": "user"|"guest", "id", "name", "isGuest" }` (`name`: a user's display name or a guest's name; `isGuest` drives the guest badge). Nothing else about an actor (no IP, no guest mode or ban flag) is in this form.

## Items, libraries, playlists, sharing

| Method | Path | Notes |
|---|---|---|
| GET | `/api/library?q=&kind=&cursor=&limit=` | The caller's own library (users only; guests have none: `401`), most recently added first → `{items:[{item:{id, kind, title, artist?, album?, durationMs?, source, youtubeId?, status, presentAsAudio}, addedAt, via, sharedBy?: actor}], nextCursor?}`. `q`: every whitespace-separated word must appear (case-insensitive substring) in the title, artist or album (≤ 200 chars, first 10 words); `kind`: `audio`\|`video` (the stored kind); `limit` 1–200, default 50. `400 invalid_query` / `invalid_kind` / `invalid_cursor` / `invalid_limit` |
| GET | `/api/users?q=&cursor=&limit=` | `library.viewAll` (`401` guests/anonymous, `403 forbidden`): users to browse, by username (case-insensitive) → `{items:[{id, username, displayName, disabled, libraryCount, playlistCount}], nextCursor?}`. `q` matches part of the username or display name (≤ 100 chars); disabled accounts are listed (marked). `limit` 1–200, default 50. `400 invalid_query` / `invalid_cursor` / `invalid_limit` |
| GET | `/api/users/{id}/library?q=&kind=&cursor=&limit=`, `/api/users/{id}/playlists?cursor=&limit=`, `/api/users/{id}/playlists/{playlistId}` | `library.viewAll`, read-only: that user's library, playlists and one playlist with its entries, exactly as `GET /api/library`, `GET /api/playlists` and `GET /api/playlists/{id}` show them to the owner (same parameters and errors). `404 user_not_found` (also for a guest's id); a playlist of someone else is `404 playlist_not_found`. Viewing doesn't count as a reference for retention |
| PUT / DELETE | `/api/library/{itemId}` | Add an item to (`via:"manual"`; `201` entry, or `200` entry if already there, unchanged), or remove it from (`204`, `404 not_in_library`), the caller's library. `404 item_not_found`. A purged or failed upload can't be added (`409 media_expired` / `item_failed`); a purged or failed YouTube item is fetched again like an import of its link (needs `library.youtube`, so `403 feature_disabled` when `ytdlp.enabled` is off; `422 youtube_failed` within 10 min of a failure). Removing sets the item's `last_referenced_at` to now |
| GET | `/api/items/{id}` | Item metadata, by direct link (any actor) → `{id, kind, title, artist?, album?, durationMs?, source, youtubeId?, status, presentAsAudio, addedAt, error?, mediaVersion, you:{inLibrary, canEdit, canPurge, canRetry}}`. `mediaVersion` is the current media version: the page plays `/media/{id}/v/{mediaVersion}/…`. `error` only for a failed item; nothing about who added it or whose libraries it is in. `404 item_not_found` |
| PATCH | `/api/items/{id}` | `{title?, artist?, album?, presentAsAudio?}` → the item. The adder while it is in their library, or `library.editAny` (`401` guests/anonymous, `403 forbidden`). Cleaned like upload metadata; `artist`/`album` `null` or blank clears them. `400 invalid_title` (missing/blank/not a string) / `invalid_artist` / `invalid_album` / `invalid_present_as_audio` / `metadata_too_long` (> 300 characters) / `unknown_field` / `not_a_video` (`presentAsAudio: true` on an audio item). Audited (`item.updated`) |
| DELETE | `/api/items/{id}` | Purge immediately: `library.purge` → `204` (also for an already purged item). Queued ingest jobs are cancelled; `409 item_busy` while a job runs. Audited (`item.purged`) |
| GET | `/api/jobs?state=&cursor=&limit=` | Users only (`401` for guests and anonymous). The encode jobs of items in the caller's library (any entry, shares included), exactly as `GET /api/admin/jobs` lists them (same parameters, shape and errors); no logs and no actions ([library-and-ingest.md](library-and-ingest.md#encode-jobs-page)) |
| GET | `/api/items/{id}/job` | Ingest status: the latest job `{id, kind, state, progress, attempts, createdAt, startedAt?, finishedAt?, log?, step?, stepProgress?}` (any actor; `log` only for those who may edit the item; `step` `download`\|`encode`\|`finish` and its own 0..1 `stepProgress` while it runs, live from the ingest queue, [library-and-ingest.md](library-and-ingest.md#ingest-job-states)). `404 item_not_found` / `job_not_found` |
| POST | `/api/items/{id}/retry` | Fetch a **failed YouTube item** again now ([library-and-ingest.md](library-and-ingest.md#retrying-a-failed-youtube-item)) → `202 {itemId, jobId, status: "pending"}`. Users who may edit the item (the adder while it is in their library, or `library.editAny`) or hold `admin.jobs` (`401` guests/anonymous, `403 forbidden`); `you.canRetry` on the item says whether the button shows. `403 feature_disabled` (`ytdlp.enabled` off), `404 item_not_found`, `409 not_youtube` (uploads can't be retried: a failed upload's file isn't kept) / `item_purged` / `ingest_in_progress` (a job is queued or running) / `item_not_failed`, `429 retry_too_soon` (one retry per item per 30 s, `Retry-After`), `507 insufficient_storage`. Audited (`item.ingest_retried`) |
| GET | `/media/{id}/v/{N}/{audio.m4a\|mezz.mp4\|original\|cover.jpg}` | **Media version N** of the file ([library-and-ingest.md](library-and-ingest.md#storage-layout-and-media-versions)), served as long as that version exists, also after the item switched to a newer one, so a play that started on it finishes on it. These are the URLs clients are given (room state `coverUrl`/`audioUrl`/`videoUrl`, the item page via `mediaVersion`). Versions only grow, so the bytes behind a versioned URL never change: `Cache-Control: private, max-age=31536000, immutable`. `N` is `0` or a number without leading zeros (else `404 not_found`); a version that is gone or never existed is `404 file_not_found`. `original` isn't versioned (one per item; served the same under any `N`, revalidated). Otherwise as below |
| GET | `/media/{id}/{audio.m4a\|mezz.mp4\|original\|cover.jpg}` | The **current** version's file. Range-capable (`ETag`, `304`), `Cache-Control: private, no-cache`. `original` is served only for audio uploads (other items' kept originals only feed re-encodes: `404 file_not_found`); its content type follows its extension. Guest rules in [libraries.md](libraries.md#media-access-rules) (`403 forbidden`, checked before the item is looked up). `404 item_not_found`, `not_found` (unknown file name), `file_not_found` (not ingested, purged, no such file) |
| GET / POST | `/api/playlists` | The caller's playlists (users only: `401` for guests/anonymous). `GET ?cursor=&limit=` → `{items:[playlist], nextCursor?}`, most recently changed first (`updatedAt`, which every rename and entry change bumps); `limit` 1–200, default 50. `POST {name, description?}` → `201 playlist`; `409 too_many_playlists` (1000 per user). A playlist is `{id, name, description?, entryCount, createdAt, updatedAt}`. `name`: cleaned like item metadata, 1–100 characters (`400 invalid_name` / `name_too_long`); `description`: line breaks kept, ≤ 2000 characters (`400 invalid_description` / `description_too_long`); `400 unknown_field` |
| GET / PATCH / DELETE | `/api/playlists/{id}` | `GET` → the playlist plus `entries:[{id, item:{…as in the library…}, addedAt}]` in order (all of them; at most 10 000). `PATCH {name?, description?}` → the playlist (`description` `null`/blank removes it). `DELETE` → `204`; every item in it gets `last_referenced_at` = now. Someone else's playlist is `404 playlist_not_found` |
| POST / PATCH / DELETE | `/api/playlists/{id}/entries[/{entryId}]` | `POST {itemId, beforeEntryId?}` → `201 entry`, before that entry or at the end; the same item may be added again (a new entry). Doesn't add the item to the library, but references it (`last_referenced_at` = now). Item rules as for `PUT /api/library/{itemId}`: `404 item_not_found`, `409 media_expired` / `item_failed` (purged / failed upload), a purged or failed YouTube item is fetched again (`library.youtube`; `403 feature_disabled`, `422 youtube_failed`). `409 playlist_full`. `PATCH {beforeEntryId: id\|null}` → the entry, moved before that entry or to the end (`null`). `409 before_entry_not_found` (not an entry of this playlist), `404 entry_not_found`. `DELETE` → `204` (the item's `last_referenced_at` = now). Positions are server-side only |
| POST | `/api/shares` | `{itemId, toUsername, message?}` → `201 share` (the sender's view). Users only (`401` guests/anonymous); any user may share any item. Adds the item to the recipient's library (`via:"share"`, `sharedBy`; an existing entry is left as it is) and references it (`last_referenced_at` = now). `toUsername` is case-insensitive; an unknown or disabled user is `404 user_not_found`; `400 cannot_share_with_self`. `message`: line breaks kept, ≤ 500 characters (`400 invalid_message` / `message_too_long`). Item rules as for `PUT /api/library/{itemId}` (`404 item_not_found`, `409 media_expired` / `item_failed`, a purged or failed YouTube item is fetched again: `403 feature_disabled`, `422 youtube_failed`). `400 invalid_item_id` / `invalid_username` / `unknown_field`. `429 too_many_shares` with `Retry-After` over 100 shares per sender per rolling hour |
| GET | `/api/shares?direction=in\|out&cursor=&limit=` | Received (`in`, the default) or sent (`out`) shares, newest first → `{items:[share], nextCursor?, unseenCount}`. A share is `{id, item:{…as in the library…}, from: actor, to: actor, message?, createdAt, seen?}`; `seen` only in the recipient's view (the sender never learns whether it was seen, nor whether the item is still in the recipient's library). `unseenCount`: the caller's received shares not yet seen (the notification badge). `limit` 1–200, default 50. `400 invalid_direction` / `invalid_cursor` / `invalid_limit` |
| POST | `/api/shares/seen` | `{ids:[shareId…]}` (≤ 200) or `{all:true}` → `{unseenCount}`: marks received shares as seen. Ids that aren't the caller's received shares are ignored. `400 invalid_ids` / `invalid_all` / `unknown_field` |

## Adding media

| Method | Path | Notes |
|---|---|---|
| POST | `/api/uploads` | `{filename, size, roomId?}` → `201 {uploadId, chunkSize, size}`. With `roomId`, the upload is a request in that room and the room's guest rules apply; guests need a `roomId` (else `401`). `413` over `ingest.maxUploadBytes` (guests: or the quota's item size), `429 upload_quota_exceeded` with `Retry-After` for guests over `guests.uploadQuota`; `507 insufficient_storage` when the free space minus `size` would fall below `storage.minFreeBytes`; guest refusals per [library-and-ingest.md](library-and-ingest.md#who-can-add-media) |
| PUT | `/api/uploads/{id}` | Chunk with `Content-Range: bytes start-end/size` → `{receivedBytes, size}`; idempotent (bytes already received are skipped); a chunk must start at or before `receivedBytes` (else `409 upload_offset_mismatch`); `507 insufficient_storage` while the free space is below `storage.minFreeBytes` (the bytes so far are kept; send the chunk again later) |
| GET | `/api/uploads/{id}` | `{receivedBytes, size, itemId?}` (`itemId` once completed) |
| POST | `/api/uploads/{id}/complete` | `{title?, artist?, addToLibrary?}` → `{itemId, deduplicated}`; repeatable. `422 unreadable_media` / `no_audio` / `too_long` (the upload is deleted) |
| POST | `/api/imports/youtube` | `{url, presentAsAudio?, addToLibrary?}` → `{itemId, cached: true\|false, status}` (`cached`: the item was already ready; `status`: `ready`, `pending` or `processing`). `400 invalid_youtube_url`, `422 youtube_live` / `too_long` / `youtube_unavailable` (yt-dlp's error), `422 youtube_failed` with `Retry-After` (failed less than 10 min ago), `503 ytdlp_unavailable`, `504 youtube_timeout`, `507 insufficient_storage` (a new video, refetch or retry while the free space is below `storage.minFreeBytes`; a ready, pending or processing item is still returned). **Lookup stages:** with `Accept: application/x-ndjson`, a request that has to run the `yt-dlp -J` lookup (a new video) is answered as a stream of JSON lines (`200`, chunked, `X-Accel-Buffering: no`) from the lookup's first stage on: `{type:"progress", stage, text}` per [stage](rooms.md#adding-a-youtube-link), then one `{type:"result", itemId, cached, status}` or `{type:"error", status, error:{code, message}, retryAfter?}` (the error the plain answer would have had). A known item (no lookup), and any error before the lookup starts, gets the plain JSON answer at once, so a client must check the `Content-Type`. Without that `Accept` the answer is always the plain one (the Library page asks for the stream) |

Inside a room, requests made by upload or YouTube go through the WebSocket `queue.add` message, which references an `uploadId` or a `youtubeUrl`. That is what writes the request and queue entry.

## Rooms

| Method | Path | Notes |
|---|---|---|
| GET | `/api/rooms?cursor=&limit=` | Anyone. Failed or expired uploads are left out. Anyone who may open the room and request from the library: guests and anonymous visitors need the effective `guests.canRequestLibrary` (`403 guest_library_requests_disabled`); with `none`, `403 library_requests_disabled` for everyone but the owner (who finds their own library). `404 room_not_found`, `403 banned_from_room`, `400 invalid_query` / `invalid_kind` / `invalid_cursor` / `invalid_limit` |
| GET | `/api/rooms/{id}/requests?source=&requester=&cursor=&limit=` | Request history ([libraries.md](libraries.md#room-owners-request-history)): users only (`401`); the owner and moderators (`rooms.moderateAny` too), else `403 forbidden`. → `{items:[request], nextCursor?}`, newest first; `limit` 1–200, default 50. `source` = `library`\|`upload`\|`youtube`, `requester` = a user's or guest's id. A request is `{id, item, requester?: actor, requesterName, via, at, entryId?, addedToOwnerLibrary, inOwnerLibrary}`: `item` as in the library (a purged one shows `status: "purged"`), `requester` with the name it had then (gone once the account or guest is deleted; `requesterName` stays), `inOwnerLibrary` = in the owner's library now however it got there. Requests older than `rooms.requestHistoryDays` are never listed. `400 invalid_source` / `invalid_requester` / `invalid_cursor` / `invalid_limit` |
| POST | `/api/rooms/{id}/requests/add-to-library` | The **owner only** (`403 forbidden` for moderators and `rooms.moderateAny`). `{requestIds:[…]}` (1–100) → `{results:[{requestId, itemId?, created?, error?:{code, message}}]}`, one per distinct id: adds the item to the owner's library (`via: "request"`, `created: false` if it was already there) and marks the request `addedToOwnerLibrary`. Each id succeeds or fails on its own: `request_not_found` (not this room's, or trimmed), `media_expired` / `item_failed` (an upload can't be restored), a purged or failed YouTube item is fetched again (needs `library.youtube`, else `forbidden` / `feature_disabled`). `400 invalid_request_ids` / `unknown_field` |
| GET / PUT / DELETE | `/api/rooms/{id}/members[/{userId}]` | Users only (`401`). `GET ?cursor=&limit=` → `{items:[{user: actor, role, joinedAt}], nextCursor?}`, owner first, then moderators, members, banned: owner and moderators (`403 forbidden`). `PUT {role: owner\|moderator\|member\|banned}` → the member (`201` if the user had no row, else `200`; `joinedAt` is kept): the owner sets any role for anyone but themselves, moderators only `member`/`banned` for users who aren't the owner or a moderator. `role: owner` **transfers the room** (owner only; the target must be an enabled account, `409 user_disabled`; the old owner becomes a moderator). `DELETE` → `204`, removes the role or lifts the ban: the owner (anyone but themselves), moderators (members and banned users), or the user themselves to leave (not the owner: `409 owner_cannot_leave`; not while banned). `404 user_not_found` / `member_not_found`, `409 cannot_change_own_role`, `400 invalid_role`. Audited (`room.member_role`, `room.member_removed`, `room.owner_transferred`) |
| POST | `/api/rooms/{id}/members` | `{username, role}` → as `PUT …/members/{userId}` for the user with that username (case-insensitive, same statuses and rules), so the management view can add members by name. `404 user_not_found` (a room the caller can't see stays `404 room_not_found`), `400 invalid_username` / `invalid_role` / `unknown_field` |
| GET | `/api/rooms/{id}/server-switches` | Users only (`401`); the owner and moderators (`rooms.moderateAny` too), else `403 forbidden`. → `{guests:{enabled, canVote, canRequestLibrary, canUpload, canYoutube}, overlay:{enabled}, outputs:{rtmp:{enabled, maxIdleStopMinutes}, ts:{enabled}, hls:{enabled}}}`: the server switches behind the room settings, so the management view greys out what the server turned off (and shows the server's cap on `outputs.rtmp.idleStopMinutes`). Each guest capability is the server setting alone (`canYoutube` also needs `ytdlp.enabled`); `guests.enabled` off turns them all off |
| GET / PUT / DELETE | `/api/rooms/{id}/guest-bans[/{guestId}]` | Users only (`401`); the owner and moderators (`rooms.moderateAny` too), else `403 forbidden`. `GET ?cursor=&limit=` → `{items:[ban], nextCursor?}`, newest first. `GET …/{guestId}` → that guest's ban, also when not banned (so the UI can warn before banning). `PUT …/{guestId}` (no body) → the ban (`201` if new, `200` if already banned). `DELETE …/{guestId}` → `204`, `404 ban_not_found`. A ban is `{guest: actor, identifiedBy: "cookie"\|"ip", banned, bannedAt?, warning?, ip?}`: `warning` for an IP-mode guest (the ban covers everyone sharing that IPv4 address or IPv6 /64), `ip` (the guest's last IP) only for *ip.view*. A ban removes the guest from the room's presence (its sockets are kicked); a banned guest gets `403 banned_from_room` and doesn't see the room listed. `404 guest_not_found`. Audited (`room.guest_banned`, `room.guest_unbanned`) |
| GET / POST / PATCH / DELETE | `/api/rooms/{id}/outputs[/{outputId}]` | `GET` (owner and moderators) → `{items:[output]}` (rtmp, ts, hls order) or one output. `POST {kind: rtmp\|ts\|hls, enabled?: true, rtmpUrl?, rtmpKey?}` → `201`, `PATCH {enabled?, rtmpUrl?, rtmpKey?}` (`rtmpKey: null` or `""` removes the key), `DELETE` → `204`: the owner only. Creating one, or turning one on, while the server switch `outputs.<kind>.enabled` is off: `403 feature_disabled` (turning off and other changes always work). RTMP needs `rtmpUrl` (`rtmp://` or `rtmps://` with a host, ≤ 2048 chars; `400 invalid_rtmp_url`); the key is printable ASCII without spaces, ≤ 512 chars (`400 invalid_rtmp_key`); RTMP fields on a ts/hls output: `400 invalid_field`. The RTMP viewer URL is the room setting `outputs.rtmp.playbackUrl`, not a field here. An output is `{id, kind, enabled, serverEnabled, active, createdAt}` plus `url` (ts/hls: `{publicBaseUrl}/live/{token}.ts` or `/live/{token}/index.m3u8`) or, for RTMP, **for the owner only** `rtmpUrl, hasRtmpKey, rtmpKey?` (the full key; moderators get none of these three, nothing about the key or the ingest URL, which can carry credentials too), `playbackUrl?`, `rtmpAvailable` (false without ffmpeg) and `status?: {state: connecting\|connected\|retrying\|error, detail?, failures, since, retryAt?}` while a push runs (moderators: `detail` without URLs or key hint, as in `output.status`), and, for the owner only, `stopped?: {reason: "idle", at, idleMinutes}` while the server's [idle stop](program-output.md#idle-stop) keeps the RTMP output off (gone once it is turned on or off again). `active` = enabled AND the server switch. `404 output_not_found` |
| POST | `/api/rooms/{id}/outputs/{outputId}/rotate` | The owner. New token (ts/hls; RTMP `409 no_token`); open `.ts` connections with the old token end at once |
| POST | `/api/diagnostics` | Anyone (CSRF origin check as usual). The room page's "Send diagnostics" (listen mode): any JSON object up to 256 KiB → `204`; the server logs it on one line as `Client diagnostics from <user id \| guest id \| anonymous>: {json}` with URL parameters such as `token=`, `key=`, `ticket=` masked, and never an IP. Rate-limited per IP (10, then one per 30 s; `429`). What the page sends: [rooms.md](rooms.md#listen-mode). `400` / `413` / `415` as for any JSON body |

## Admin

| Path | Notes |

## Live (no session; token in path)

`GET/HEAD /live/{token}.ts` · `GET /live/{token}/index.m3u8` · `GET /live/{token}/seg/{seq}.ts`

Every request counts against a per-IP rate limit (burst 60, then 10/s; IPv6 by /64) before the token is looked up: `429 rate_limited` with `Retry-After`. A token has at most 64 concurrent connections (`.ts` streams for their whole life, HLS requests while served): `429 too_many_connections`, `Retry-After: 10`. Unknown, disabled or rotated tokens, and kinds the server switched off: `404`.

## WebSocket

`GET /ws` (upgrade; `sid` or `gid` cookie, or anonymous). One room per socket. Requests carry `"rid"`, and are answered with `ack` or `error`.

Actions that need an identity (votes, requests, suggestions, vote-skip) are refused from an anonymous socket with error code `identity_required`. The client then calls `POST /api/me/guest`. That sets the `gid` cookie in cookie mode, and returns a single-use `identityTicket` valid for 60 s. The client sends `{type:"identity", ticket}` on the open socket and retries the action. The ticket is needed because a socket that's already open can't see a cookie set after its upgrade.

### As implemented (M3, `rooms/RoomSocket`, `RoomBroadcaster`)

- **On connect** the server sends `{type:"identity", actor?}` (no `actor` for an anonymous socket). `auth` (bearer token) is only accepted before `join` (`409 already_joined`); a bad token is `401 invalid_token`. An invalid `Authorization: Bearer` header on the upgrade is a plain HTTP `401`, never a socket.
- **`identity`**: `400 invalid_ticket` (unknown, used, expired), `409 already_identified` (a user socket, or another guest), `403 guests_disabled`. A socket in a room is then counted as the guest and gets a fresh full `state`; a guest banned from the room gets `kicked` instead.
- **Identity re-check**: before every room action the socket's session or guest is resolved again. A revoked/expired session, disabled user or deleted guest gets `kicked` `session_ended`, an `error` `session_ended`, and the socket closes (1000).
- **Replies**: `{type:"ack", rid, ...result}` / `{type:"error", rid?, status, code, message}`; `rid` may be a number or a string. Without a `rid` only errors are sent. Results: `join` → `roomId, slug, mode`; `queue.add` → `entryId, itemId, state` (`queued`/`suggested`); `queue.addPlaylist` → `entryIds, skipped`; `queue.move` → `moved`; `queue.pin` → `changed` (optional `pinned`, default `true`; `false` unpins); `vote` → `votes` (the new total); `voteSkip` → `votes, needed, skipped`; `play`/`pause`/`previous` → `changed`. Other codes: `400 invalid_message` (not a JSON object, missing/mistyped field), `409 not_joined`, `400 invalid_mode`, `400 invalid_position`, `400 invalid_vote`, `503 room_closed` (join again), `429 too_many_requests` (more than 4 `queue.add`/`queue.addPlaylist` running per socket; those two run off the socket's thread so `time` is answered meanwhile). `time` needs a numeric `t0`; it is answered at any time, also before `join`.
- **`join`**: `room` is the id or slug, `mode` defaults to `listen`. Joining another room leaves the first. Access is `GET /api/rooms/{room}`'s (`404 room_not_found` for private rooms, `403 banned_from_room`).
- **Messages per change**: every committed change sends each socket in the room exactly one message with the new `version` (consecutive): `presence` (`{presence}`) when only the counts changed; `timeline` (`{timeline, current?, skipVotes?}`) when only the timeline was re-anchored on the same entry; otherwise the full `state` while the room has at most 200 waiting entries (queue + suggestions), and above that a `queue` delta: `{upsert: [entries new or changed], removed: [entryIds], order: [queue entryIds in play order], suggestionOrder: [...], timeline, current?, history, skipVotes?, presence}` (instead of the per-op `add|remove|move|votes|status` sketch above). Room, settings and member-role changes always send the full `state`. The `state` sent on `join` carries the version before the join, the join's own presence change follows as `presence`. `sync` re-sends the full `state` (same version).
- **`state` shape**: `room: {id, slug, name, visibility, controlMode, ownerId, settings, you: {role?, identified, canVote, canRequest, canUpload, canYoutube, canSkip, canModerate}}`, `timeline: {state, entryId?, anchorServerMs, anchorPositionMs}`, `current?: {entryId, status, item, addedBy?, addedAt}` (absent when idle), `queue`/`suggestions: [{entryId, status: ready|processing|failed|purged, item, addedBy?, addedAt, votes, pinned, yourVote}]` (queue in play order, suggestions oldest first), `history: [{entryId, state: played|skipped, item, addedBy?, playedAt}]` (last 20, latest first), `skipVotes?: {entryId, votes, needed}` (vote mode with vote-skip on), `presence`, `outputs: []` (filled in M4; `overlay` comes with M5). `item`: `{id, kind, presentAsAudio, title, artist?, durationMs?, status, source}` plus, once `ready`, `coverUrl`, `audioUrl`, `videoUrl` (video items; all three are the current media version's URLs, `/media/{id}/v/{N}/…`, so a play that started on them keeps its bytes after a re-encode) and, for audio uploads with a web-playable original, `originalUrl` + `originalGainDb` + `originalType` (the MIME type for `canPlayType`, by the kept file's extension, e.g. `audio/flac`, `audio/mp4; codecs="mp4a.40.2"`, `audio/ogg; codecs="opus"`; absent for an unlisted extension, the client then trusts the server).
- **`outputs` and `output.status`** (M4, `rooms/RoomOutputs`, `output/OutputStatusFeed`): `state.outputs` lists the room's **active** outputs (row enabled AND server switch), in the order rtmp, ts, hls: `{kind, status, estimatedDelayMs, detail?}`. `status`: RTMP `connecting` (also before the push has started) | `connected` | `retrying` | `error` (also when the server has no ffmpeg); `.ts`/HLS `ready`. `estimatedDelayMs` is the room setting `estimatedDelayMs.<kind>` (defaults 5000 / 2000 / 8000). `detail` (RTMP: the push's last ffmpeg line, key masked, or why it can't run) goes to the owner and moderators only; moderators get it with every URL replaced by `(ingest URL)` and no key hint (`RoomOutputs.moderatorDetail`), since the ingest URL and key are the owner's. A change sends `{type:"output.status", kind, status, estimatedDelayMs?, detail?}` to every socket in the room, **without a `version`** (not a room change; the client applies it to its state as is); an output that stops being active is sent once as `status: "off"` (no delay). Changes are found by comparing each room's outputs with what was last sent, after every push status change and after every outputs reconcile (API changes, admin settings saves, every 10 s). A delay setting change comes with the room's full `state`.
- **`queue.retry`** (added 2026-11-10): `{entryId}` of a queued entry or suggestion whose YouTube item failed → `ack {itemId, status: "pending"}`; the item gets a new download job, the entry keeps its place and shows "Waiting to download…" again (with the next `state`/`ingest`), and plays once ready like any entry that isn't ready. Allowed for the owner and moderators, and for whoever requested the entry while they may still add YouTube links in the room (`you.canYoutube`: a user with `library.youtube`, a guest while the server's and the room's `guests.canYoutube` allow it); others `403 forbidden`, anonymous `401 identity_required`. Errors as `POST /api/items/{id}/retry` (`404 entry_not_found` for an unknown entry). Runs off the socket's thread like `queue.add` (it can wait for an import of the same video) and counts toward the same limit of 4. Audited (`item.ingest_retried`, details with `roomId`). `item` in the room state now also carries `source` (`upload`|`youtube`), so the client knows which failed entries have a Retry button.
- **`request.new`**: `{request: {id, entryId, item, by?, via}}` to sockets of the owner and moderators (no `version`; it accompanies the change's own message).
- **`request.progress`** (added 2026-11-10): while a `queue.add` with a `youtubeUrl` runs the `yt-dlp -J` lookup of a new video, `{type:"request.progress", rid, stage, text}` for each lookup stage, in order and each at most once, **to the requesting socket only** and before the request's `ack`/`error`; nothing without a `rid`, and nothing when there is no lookup (a known item answers at once). `stage`/`text`: `contacting` "Contacting YouTube…", `page` "Reading the video page…", `details` "Getting the video details…", `formats` "Checking formats…" ([rooms.md](rooms.md#adding-a-youtube-link)). The spec's sketch named the field `id`; it is `rid`, like `ack`.
- **`ingest`** (added 2026-11-10, `RoomBroadcaster`, `ingest/IngestProgress`): what the ingest of the room's entries whose item isn't ready (current, queued and suggested; `processing` or `failed`, not `purged`) is doing, `{type:"ingest", items: {<itemId>: {state: queued|running|failed, kind?, position?, step?, progress?, error?}}}`, to every socket in the room, **without a `version`** (not a room change). `queued`: `position` is the 1-based place in the whole ingest queue (the jobs page's); `running`: `step` `download`|`encode`|`finish` with that step's own `progress` (0..1, whole percent) once the job has named one; `failed`: `error`, the item's error cut to its first line and 120 characters. An item with no job yet is absent (it reads as waiting). Looked up at most once a second per room and only while such an entry exists; sent only when it changed, right after the full `state` to a socket that joins or `sync`s, and once more with `items: {}` when no entry waits any more. No logs, nothing about other people, no IPs. The web client shows it on the entry's badge ("Waiting to download (3rd in line)", "Downloading 45 %", "Encoding 30 %", "Finishing…", "Failed: …"; `web/src/jobtext.ts` `ingestText`, also used by the Library and item pages).
- **`kicked`** (`{reason}`) takes the socket out of the room; the socket stays open. Reasons: `banned_from_room` (guest ban, or a user banned via the members API), `room_not_found` (e.g. the room went private), `room_deleted`, `room_closed` (the room's executor stopped; join again), `session_ended` (then closed). Role changes (`PUT`/`DELETE …/members/{userId}`) now go through the room executor as a `MemberChanged` event, so they bump the room `version`.
- **Slow sockets**: each socket has a bounded outbox (1024 messages); one that overflows is closed with 1008.
