## Single-page app

(Siggi, 2026-11-14.)

- **One document.** Every UI URL (`/`, playlists, rooms, settings, admin, …) gets the same HTML shell from the server; client-side routing (History API) decides what to show. Moving around never loads another document, so a room keeps playing without a break.
- **Logging in doesn't reload either.** After login the page fetches the new identity and re-identifies itself (API state, the room socket: reconnect or re-authenticate it), and playback continues through the switch. A guest who logs in inside a room is offered the guest merge ([auth.md](auth.md)) without leaving the page.
- **Logins on another origin** (OIDC / plain OAuth) open in a **popup window** (opened directly from the click, so popup blockers allow it). The callback page in the popup tells the opener (same-origin `postMessage`, or a `BroadcastChannel`) that the login finished, or why it failed, and closes itself. If the popup is blocked, the page says so and offers the full-page redirect as a fallback (which does reload).
- **Logging out reloads the document**, so nothing from the logged-in state lingers.

**As built** (M9 SPA step, 2026-11-14): the server sends `web/static/index.html` for every UI path (`StaticFiles.isAppPath`: not under `/api/`, `/media/`, `/live/`, `/auth/`, `/r/`, `/ws`, `/test/`, `/js/`, `/css/`, not file-like; [api.md](api.md)). It holds the header nav, `<main id="app">` and one `<template id="view-…">` per view; `/js/app.js` starts the shell (`web/src/shell.ts`). The router (`web/src/router.ts`, DOM-free, `router.test.mjs`) maps paths to views: `/` home, `/login`, `/register`, `/password`, `/setup`, `/rooms/`, `/rooms/{ref}`, `/rooms/{ref}/manage`, `/library/`, `/playlists/`, `/playlists/{id}` (playlist deep link; `?id=` still works), `/encodes/`, `/account/`, `/admin/`, `/items/{id}`, anything else the Not found view; the old spellings (`/login.html`, `/library` without the slash, …) are aliases, replaced in the address bar. A view = its template cloned into `#app` plus its module imported under a fresh `?mount=N` (a new module instance per visit); the previous view's signal (nav.ts) is aborted and its element removed. Every view module takes `viewScope(import.meta.url)` synchronously at its start (its signal, path and query, and its elements, looked up inside the view's own element; after an `await`, `pageSignal()` and `location` may already be the next view's): every timer, poller (`watchItem`, `mountJobs`), subscription and window/document listener ends with that signal, and async work that finishes after it renders nothing, so a view taken away never draws into the next one (the M9 "old views keep running" fix). Links, `navigate()` / `reloadPage()` and plain GET forms go through `decide()`; back/forward through popstate (scroll positions in `history.state`). The room view keeps playing while other views are shown (see [rooms.md](rooms.md#playback-across-pages-web)). Since the "Login without reload" step, login/register/password/setup are views like any other, also while a room plays.

**Login as built** (M9 "Login without reload", 2026-11-14):
- **Re-identifying:** the login, register and setup views call `nav.ts` `identityChanged()` after success; the shell (`#identityChanged`) reloads who is here, redraws the frame (`Frame.identityChanged()`: sidebar, search, account menu) and calls the followed room's `ShellRoom.reidentify()`: the room view loads `/api/me`, joins the room's play session for a user (`shouldJoin`, so a guest who logs in inside a room is then in that room as a user), sets the socket's actor and calls `RoomConnection.reconnect()` (a new socket at once, without the "connection lost" state; the server identifies a socket by its cookie when it opens, and the join brings the state again). The player isn't touched, so playback goes on. Only when the followed room is the **previous user's alone room** (an account switch) is it stopped, and the new user's play-session room starts in the background as usual. Then the view goes to `?next=` (or the change-password view for a temporary password).
- **Guest merge in place:** `offerGuestMerge()` is a small dialog over the page (`.merge-prompt`, "Move them" / "Not now", then the summary), no `window.confirm` (which would block the page's scripts while it is open).
- **Provider logins in a popup:** each provider is a link to the full-page start URL; a plain click instead opens `window.open(start + "?popup=1", "togethertunes-login", "popup=yes,width=520,height=700")` right in the click handler. The server keeps `popup` with the pending login (logins only, ignored for `intent=link`) and ends it at `GET /auth/popup-done` (success) or `/auth/popup-done?error=<code>` (any failure, also at the start), instead of `next` or `/login?error=`. That page (served by `OidcLogin`, no inline script, `no-store`) runs `popupdone.ts`: it posts `{type: "togethertunes.login", id, ok, error?}` to `window.opener` with target origin `location.origin`, and on the `BroadcastChannel` `togethertunes.login` (providers whose pages set `Cross-Origin-Opener-Policy` cut the opener link; Safari before 15.4 has no BroadcastChannel and relies on the opener), then closes itself (text with a link if it can't tell anyone). The login view accepts only same-origin messages of that type (`parseLoginMessage`, `providers.ts`), handles each `id` once, and then continues as after a password login (or shows `providerErrorMessage(code)`). **A blocked popup** (`window.open` returns null) shows "The login window was blocked…" with a link to the full-page login, which reloads. Linking a provider from the account page still uses the full-page redirect.
- **Logout** still reloads the document (`location.assign("/")`).
- The login, register, password and setup forms have `method="post"` and their submit handlers are attached before the view's first request, so an early submit can never become a GET with the password in the URL.

  - **Recents:** Now Playing, then **Earlier** (the room's history), each with a heart.
  - **Room:** the people in the room. Right-click a person for the moderation menu (below).

  - **Change** (Siggi, 2026-11-15): on desktop the extra mute button in the middle is gone (the one beside the volume slider does the same, with the same right-click menu); without control the middle shows only the heart. In the mobile mini player, where the volume slider and its mute are hidden, the middle mute stays. - **Now Playing View** fills the window to its edges. Videos are letterboxed by default. Audio items (or Audio Only) show a view like the stream's item card.
  - (Siggi, 2026-11-15) It has **its own URL** (the room's path + `/now-playing`) and history entry. The **player bar** shows while the mouse has moved in the last **5 seconds** (or a tap on touch screens), otherwise it hides (and so does the cursor over the video). Its background there is translucent black.
  - **As built** (2026-11-15): `/rooms/{ref}/now-playing` is the `room` router view with `params.now = "1"` (`router.ts routeOf`, `isNowPlaying`, `nowPlayingPath`; the server already sends `index.html` for it, and a room whose slug is `now-playing` stays `/rooms/now-playing`).   - **As built** (2026-11-15): the ⋯ menu's **Show QR code** checkbox (`#pb-show-qr`) shows only while the Now Playing View is open and the room's layout says `available` (server switch on, mode not `off`, not the alone room); its state is kept in `localStorage` (`togethertunes.showQr`, try/catch). While on and the stream shows the overlay now (`overlayshow.ts overlayShown`, fed by the room state and its `current.overlay`), `frame.ts #drawQr` puts an SVG (`#now-qr`, `pointer-events: none`, below the "Click to enable sound" layer and the Close button) on the output frame's rectangle over the visible video (its own size, letterboxed as the stream does) or over the card (Audio Only and audio items: a frame-aspect rectangle fitted into the view), placed again on every 250 ms tick so resizes and video size changes follow. Not in the right panel, the room view or the mobile Now Playing tab.

**As built** (M9 desktop layout step, 2026-11-14): the frame lives in `index.html` around `<main id="app">` and is drawn by `web/src/frame.ts` (rules in the DOM-free `panels.ts`, `panels.test.mjs`). The sidebar shows for signed-in users; the right panel and the player bar follow **the room the room view has open** (shown, or playing in the background as before): the frame has no socket of its own, it reads that view's room state and sends through its socket (`nav.ts` `ShellRoom`), so until the "Alone" step the player bar without a room says "Not in a room". The old mini player is gone (the player bar, and **Leave** next to the room name at the top of the right panel, replace it). The video panel holds the player's `#room-player` (moved out of the room view); it shows only while a video is visible. Volume (squared slider, remembered per browser) and mute are the listener's own gain after the player's meters (`ListenPlayer.setVolume` / `setMuted`, a master gain with Web Audio, the element volume without), so muting never looks like a silent Web Audio path. **Mute only until end of song** unmutes when another entry (or nothing) becomes current. The **Room** tab lists the people present (`presence.people`, [api.md](api.md#server--client)). Autoplay dots in the sidebar show the user's own selections in the current room (read-only until the interactions step); **New Playlist** asks for a name (`prompt`) and opens the new playlist. Double-click, multi-select, right-click menus and drag and drop come with the next steps. **Window-filling layout as built** (desktop layout fixes step, 2026-11-14): from 800 px up (`@media (min-width: 800px)` at the end of main.css) `html` and `body` are the window's height with `overflow: hidden`; the body is a flex column (header, then `.app-body` filling the rest, with room for the fixed player bar below); in `.app-body` the sidebar and the right panel each scroll on their own and `#app` takes all the width between them (no `max-width`, so the right panel sits at the window's edge) and is the scroll container. Popup menus open above their button when the window has no room below (`touch.ts placeMenu`), and a ⋯ menu closes when something under it scrolls. The mobile layout is unchanged (the window scrolls).

## Header search

(Siggi, 2026-11-23.) The header's search box shows a **dropdown** of results under it:

- **1 s after the user stops typing** (2 or more characters after trimming; each keystroke restarts the wait; only the newest answer is shown, an older one arriving late is dropped) it asks `GET /api/search?q=…&limit=8` (the whole server, the caller's own library first) and shows the results: cover, title, artist; a click opens the item page, ⋯ / right-click gives the song menu as in the lists (without Select). "Searching…" while it loads, "Nothing found." when empty, and **See all results** at the bottom (= Enter).
- At the **top**, **Search YouTube** (only for people who may import YouTube links: signed in with `library.youtube`, `ytdlp.enabled` on) **replaces the results** with YouTube results (`GET /api/youtube/search`, [api.md](api.md#items-libraries-playlists-sharing)); "← Library results" goes back. Library items are not marked or merged into them: YouTube results are their own list.
- **Double-click** on a row adds it to the room open here, as double-click does in the lists ([interaction rules](#interaction-rules-all-layouts)): a library row is requested (alone, the `doubleClickAlone` setting), with the lists' notice ("1 song added to <room>."); a YouTube row does its **Add to Queue** where that action is shown. Where a double-click would add the row, a single click on a library row opens its item page only after the lists' 300 ms wait (a second click cancels it); without a room (or the right to request there) a double-click does nothing more than a click, and a click opens the row at once.
- **Escape** or a click outside closes it (while a row's ⋯ / right-click menu is open, a click outside closes only the menu; the next one closes the dropdown); **↑/↓** move through the rows (past the last one back to the box), **Enter on a row** opens it (a YouTube row: its watch page in a new tab). Typing again closes it (also the YouTube results) and waits 1 s again.
- **Enter** with no row chosen opens the full search page `/search?q=` as before. For the same people the page also runs a YouTube search and shows it in a **YouTube** section below the library results (10 results); others see the page as before.
- **YouTube result rows** (dropdown and page): thumbnail, title, "uploader · length", **Preview on YT** (the watch page in a new tab, `rel="noopener noreferrer"`) and the actions **Add to Queue** (only while a room is open here and the person may request YouTube links in it, not banned or timed out there: `queue.add {youtubeUrl}`, the room's normal request/suggest path; alone, the double-click setting's action: play now or queue) and **Add to library…** (the Add from link dialog with that link, including the type question for an uncategorized video). On the page (desktop) the rows also **drag out as links** (onto playlists, the built-in lists, the queue: the same as a link dragged in from outside).
- Searches count against **`youtubeSearch.maxPerHour`** (admin setting, default 60 per person, [auth.md](auth.md#server-settings)); over it, "Too many YouTube searches in the past hour."
- **As built** (2026-11-23): `searchbox.ts` (`HeaderSearch`, set up by `frame.ts`, closed on every view change) draws the dropdown inside the header's `#app-search` form (`#app-search-drop`, absolutely positioned; the box gets `aria-expanded` / `aria-controls` / `aria-activedescendant`); the form's own submit handler runs before the shell's, so Enter on a chosen row opens it and otherwise the shell turns the GET submit into the `/search?q=` view as before. `ytrows.ts` draws the YouTube rows for both places; `libview.ts showYoutube` fills `#list-youtube` once per page (not again when the list is re-sorted). The rules are in the DOM-free `searchdrop.ts` (`SearchTimer`, `Latest`, `moveActive`, `enterAction`, `dropStatus`, the paths; `searchdrop.test.mjs`) and `ytsearch.ts` (`canSearchYoutube`, `youtubeRow` / `youtubeDetail`, `youtubeActions`, `queuedText`, `youtubeErrorText`; `ytsearch.test.mjs`), which reuses `videosearch.ts`'s length text, preview URL and thumbnail fallback. `songmenu.ts queueItem` takes a YouTube link as well as an item id. **Search dropdown fixes** (2026-11-23): one stacking order in `main.css`'s `:root` variables, `--z-search-drop` (50) < `--z-menu` (80: `.menu`, the popup menus of `touch.ts`, also their narrow-window sheet) < `--z-dialog` (100: `.classify-prompt` and the boxes that share it); the popup menus used to sit at 40, under the dropdown. Double-click: `searchdrop.ts rowDoubleClickAdds(mode, room)` and `ClickOpener` (the click's wait, `interactions.ts OPEN_CLICK_DELAY_MS`, also used by the lists) and `interactions.ts doubleClickText` (the lists' notice); `ytrows.ts`'s `doubleClickAdds` option (the dropdown only; the search page's YouTube rows don't add on double-click). The dropdown's outside-click listener runs in the capture phase and leaves the dropdown open while a menu is open (`touch.ts menuIsOpen`).

## Interaction rules (all layouts)

- **Requesting:** double-click (double-tap) an item in a playlist or in search results to request it in the current room.
- **Alone**, double-click does what the user chose in their **user settings** (stored on the server per user; default **Play immediately**):
  - **Play immediately:** the item starts playing now.
  - **Queue it:** the item is added to the bottom of the **manually added** section of the queue. Manually added items always come before the queue's other items (e.g. autoplay songs).
- **Touch:** everything on a right-click menu is also on a **⋯** button (people, songs, the mute button). **Long press** a playlist toggles it for autoplay; its ⋯ menu has **Use only this one for autoplay** (the double-click's job).
- **Multi-select:** select several items (Shift/Ctrl/Cmd-click on desktop; a **Select** mode with checkboxes on touch) for **Add to Queue** and similar actions.

**As built** (M9 interactions step, 2026-11-14; rules in the DOM-free `web/src/interactions.ts`, `interactions.test.mjs`): **double-click** a song row in any list (playlist, Liked Songs, All My Songs, search, …) requests it in the room open here; in the user's alone room it plays it now (added, moved before the first manually added entry, then `next`) or queues it, by `doubleClickAlone`. A single click on a song's title opens its item page after 300 ms (a double-click cancels that). **Desktop multi-select:** click selects a row, Ctrl/Cmd-click toggles one, Shift-click selects a range; a bar ("N songs selected", Add to Queue in list order, Cancel; Escape clears) shows while something is selected. **Right-click menus** (each also on a ⋯ and long press): songs (Add to Queue, or alone Play now / Add to Queue; Open; Copy link; Remove from playlist / from Liked Songs / from library…; Select), playlists in the sidebar (Use / Stop using for autoplay, Use only this one, Open, Rename…, Delete…; Liked Songs without the last two), queue entries (vote, **Pin to top** / Unpin in vote mode for the owner and moderators, Request it, Retry, Remove, Accept / Reject / Withdraw for suggestions, Skip for Now Playing, Open; a ⋯ on every entry), people (the moderation menu) and mute. **Autoplay selection:** with a room open, the dot before each of the user's playlists (Liked Songs included, once it exists) is a toggle button; Ctrl/Cmd-click toggles, double-click makes it the only one, a plain click opens it; on touch a long press toggles it.

## Alone and in rooms

- A user doesn't have to be in a room: **alone**, they play their own music with their own play status (current song, position, paused or playing) and queue. The alone state lives **on the server** (per user), so it follows the user to another device. **Guests can't be alone:** they only exist inside rooms (they have no library).
- **Recents while alone** shows the user's own play history; songs that played in a room say which room.
- **Joining a room** while alone saves the alone play status and queue.
- **Creating a room** moves the current song and queue into the new room.
- **Leaving a room** to be alone (leaving, or the room being deleted, without joining another one) asks: **fork** the room's current play session and queue into the alone state, or **restore** the saved alone state.

**As built** (M9 alone and switching rooms step, 2026-11-14; rules in the DOM-free `web/src/alone.ts`, `alone.test.mjs`): the alone state plays through the ordinary room view and player. Whenever a signed-in user has no room view open, the shell (`shell.ts`) starts one **in the background** (hidden from the start; `nav.ts viewStart` gives it its own path and signal) for the play session's room: the room they are in, otherwise their alone room. The right panel then says **On your own** (no Leave, no Manage Room), and **Recents** shows Now Playing and the user's play history (`GET /api/me/history`), songs from a room with "in <room>" (linked while it exists). Following another room's link **switches rooms in place** (no new document; the old room view goes) and joins it (`POST /api/me/play-session/join`, which saves the alone state). **New Room** sends `moveAloneSession: true`. **Leave** asks fork or restore in a small dialog (Cancel keeps the room), then the alone room plays; a room deleted while the user is in it asks the same (no Cancel). The Rooms tab and the `/rooms/` page list rooms with their listener counts and a search box (an unlisted room's exact link name or link comes first).

**One window with sound per person** (Siggi, 2026-11-15): only one browser window of the same account (or the same guest) plays sound at a time, on the same device or another. A window opened while another of that account has sound **loads no media at all** (Siggi, 2026-11-23; before that it played muted in sync, downloading for nothing): no audio or video is requested, nothing is preloaded, and it has no system media controls of its own (the window that plays owns them). Everything else stays live from the room state: Now Playing, the queue, the progress bar and times (from the room's timeline), the player bar's controls. The video area shows the item's **card** (cover, title, artist) with **Move player here**; clicking it takes the sound and, in the same click, starts this window's player (video or audio only, as this window plays) at the room's position, while the window that had it drops its media the same way and shows the card and **Move player here**. **Click to enable sound** stays for the browser's autoplay block only; when both apply, **Move player here** shows (its click also enables sound). The first window that plays gets the sound without a click. A reload or reconnect of the window that has the sound keeps it; when it closes, the others stay unloaded until one is clicked. This is separate from the listener's own mute and volume and from a preview's duck. Anonymous visitors (no account, no guest) aren't affected.

**As built** (2026-11-15): the server keeps the holder per user or guest in memory (`rooms/SoundHolders`, messages `sound` / `sound.claim` / `sound.released` in [api.md](api.md#websocket)); the window id lives in the window's `sessionStorage` (`tt.windowId`), and the holder window keeps the sound for 10 s after its last socket closes (a reload). Since 2026-11-23 the other windows load nothing (rules in the DOM-free `soundwindow.ts`, `soundwindow.test.mjs`; the player in `listenplayer.test.mjs`): the window is `here`, `elsewhere` or `unknown` (between the join's state and its `sound` message, so a window that turns out not to have the sound makes no media request; an anonymous socket or a window without a window id is always `here`). Only `here` lets the player (`listen.ts`) load anything; otherwise every element is emptied (`src` removed and `load()`ed, the Web Audio graph kept), with no preload and, with no element playing, no audio-health or stall handling, and `heard` is false, so the Media Session stays empty. The overlay says **Move player here** while `elsewhere` and the room has a ready current entry (also paused), and the frame shows the card behind it (as for the autoplay block). Its click sends `sound.claim` (again after a reconnect if it didn't get through), makes the window `here`, loads the current entry and runs the usual unlock (seek to the timeline, `play()`) in the same gesture; with "Tap to restore sound" pending it rebuilds without Web Audio instead, which loads the entry too. The progress bar and times were already computed from the timeline. A preview's ducking stays local to its window.

## Autoplay from playlists

- Autoplay belongs to the **current room**. The owner and the users the owner allows (room setting: **owner only**, **moderators**, or **every member**) pick which playlists autoplay draws from; each person selects among **their own** playlists in the Library tab. Single click opens a playlist; **double-click** makes it that person's only autoplay playlist (it clears only **their own** other selections, never other people's); **Ctrl-click** (Cmd-click on macOS) toggles one. Any number can be selected, including zero (then that person contributes nothing). The dot in front of a playlist marks it as selected.
- Other people's playlists are invisible, **except** those selected for autoplay in the room (listed at the bottom of the Library tab).
- **Autoplay stops when nobody is there** (Siggi, 2026-11-15): the timer starts when **no web users are in the room** (nobody has the room open in the web UI: no room socket of a signed-in user, guest or anonymous visitor, a background/alone room view included; hidden tabs count as present) and resets when someone comes back. After the room's **`autoplay.stopAfterMinutes`** (default **120**) autoplay stops topping up the queue; what is already queued and every request still play, then the room goes idle, and the outputs turn off by the idle rule ([program-output.md](program-output.md#auto-turn-off)). The admin caps the minutes with **`autoplay.maxStopAfterMinutes`** (default **180**). Room setting **`autoplay.pullListenersCount`** (owner, default off): `.ts`, HLS and MP3 listeners count as people in the room too (the timer starts only when there are no web users **and** no pull listeners); in this mode the cap is the admin's **`autoplay.maxStopAfterMinutesWithListeners`** (default **15**). Once stopped, the room says so ("Autoplay stopped: nobody was here for 2 h") with **Resume autoplay** (people who may select playlists); it also resumes by itself when a web user comes back into the room (a turned-off output stays off, as before).
  - **As built** (2026-11-15, `rooms/AutoplayStop`, details in [rooms.md](rooms.md#autoplay)): the clock is per loaded room (`RoomPresence.emptySince`; at server start a room loaded with nobody in it starts it at its load); only a **playing** room with `autoplay.upcoming` > 0 is stopped, checked every 10 s. The limit is `min(autoplay.stopAfterMinutes, cap)`; a higher room value is saved and Manage Room says the cap applies. The stop is saved with the room (`rooms.autoplay_stopped_*`, migration 0034) and sent as `room.autoplayStopped: {at, reason: "nobody", minutes}`; the Queue (right panel and room view, the From Playlist section) shows "Autoplay stopped: nobody was here for 2 h." and, for people who may select playlists (`you.canResumeAutoplay`), a **Resume autoplay** button (`autoplay.resume`; also `POST /api/rooms/{id}/autoplay/resume`). Manage Room → Settings has an **Autoplay** group with the minutes (and the cap note) and "Stream listeners count as people in the room"; the admin's Settings tab has the two caps in an Autoplay group. The other autoplay settings (`selectors`, `upcoming`, `mix`, `recentPct`, `requestsFirst`) still have no form field there; they are API-only for now.
- **Always shuffled.** With several playlists, a room setting picks **fully random** (one pool) or **take turns** (between the **people** who selected playlists; each turn picks from that person's selection).
- **Liked Songs** can be selected for autoplay like any other playlist (it is an ordinary playlist row in the database).
- **Upcoming songs:** a room setting gives how many "From Playlist" songs to show; when fewer are upcoming, autoplay adds more to fill it up.
- **Recently played** songs get weight 0 right after playing in the room, and their weight **ramps up gradually** to full until their last play is X songs ago, where X is a room setting in percent of the songs available to autoplay (default 50 %).
- **Requests vs. autoplay:** a room setting: requests always play first, or alternate between a request and an autoplay song.
- **Removing:** × deletes an entry from the queue: the owner, a moderator, or the user who added it. For an autoplay entry, the person whose playlist it came from counts as the one who added it.
- **Votes:** the number next to ↑ is the entry's votes; ↑ is the vote button.

## Moderation menu (right-click a person in the Room tab)

- **Add / Remove Moderator**.
- **Timeout:** for a length the moderator types in (any duration).
- **Ban:** until unbanned.
- A timeout or ban puts the room into a **read-only state** for that person: they can still be in the room and listen, but can't request, vote, like into the room's queue or otherwise change anything in it.
- **Room bans follow the IP address** (Siggi, 2026-11-14; the IP key as elsewhere: IPv4 address or IPv6 /64, stored like `guests.key_hash`, never shown without `ip.view`):
  - Banning a **guest** bans their IP address in the room.
  - Banning a **logged-in user** bans their account **and** their current IP address in the room.
  - A logged-in user who isn't banned but comes from a banned IP address is **treated as banned**, unless the room has added them as a **member**.
  - Unbanning lifts the account and the IP address together. Timeouts work the same way.
- **Ban from server:** admins only; disables the user's account.
- As implemented: [rooms.md](rooms.md#bans-and-timeouts) (`/api/rooms/{id}/bans/...`; Ban from server is `PATCH /api/admin/users/{id} {disabled: true}`, shown to holders of *admin.users*).
- (Future ideas, not in M9: ban a whole home server from the room, or from the server; see [future-ideas.md](future-ideas.md).)

## Library rules

- **Liked Songs** is a built-in playlist per user. A heart adds the song to it. **Guests can't heart songs** (no heart shown for them).
- **Guest merge** (when a guest logs in or registers in the browser holding the guest cookie, [auth.md](auth.md)) also moves **the items the guest added** to the account (`added_by`, so they can still edit them) and adds them to the account's library, as well as the items of the guest's **link and file requests** (also when someone else fetched them first).
- **Link and file requests** (Request Link, links and files dropped on the queue or the room view) by a signed-in user also add the item to their library, without a type question: a video of unknown type goes in uncategorized ([libraries.md](libraries.md)).
- **An item in a playlist is always in the library of the playlist's owner** (this replaces "adding to a playlist doesn't add it to your library", [libraries.md](libraries.md#playlists)). So adding to a playlist asks for a type for an uncategorized video ([media-types.md](media-types.md)).
- **+ Add from link** adds to the open playlist and to the library.
- **Links from other music services** (Siggi, 2026-11-22): the Request Link box and Add from link also take Spotify and TIDAL track links when the admin has set up the link resolver ([library-and-ingest.md](library-and-ingest.md#links-from-other-music-services)). Under both fields a hint: "A link to a song or video from YouTube or other music services." (never naming the services). The resolver's errors are the server's messages, shown like the other import errors. There is no client-side check of which links work (the URL field only needs a URL; the server decides), so nothing else changed in the page.

## Requests-only mode

- **Remote mode** is renamed **Requests-only mode**: the page plays nothing and is used for requests and votes (e.g. for people hearing the room through a stream).
- The room owner can **force** everyone into it (e.g. a party where the room plays on one speaker). Then the room's pages play nothing. **Authenticated users are never refused media.** Only **unauthenticated** visitors (guests, anonymous) get `403` for the room's media when they have no other reason to access the file.
- As built (M9 backend step): the room setting `requestsOnly` (off by default; Manage Room → Playback, "Requests-only room"). **API names stay `remote`** (`?mode=remote`, the socket's `mode`, `presence.remote`); only user-visible text says requests-only. "No other reason" = another room they are in, not forcing it, where the item is current or next. Details in [rooms.md](rooms.md#remote-mode) and [libraries.md](libraries.md#media-access-rules).
